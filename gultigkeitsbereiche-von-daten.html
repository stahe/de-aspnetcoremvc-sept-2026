    6. Gültigkeitsbereiche von Daten

    Eine Webanwendung bedient viele Benutzer gleichzeitig, und jeder Benutzer sendet zahlreiche Anfragen. Daten können daher auf drei Ebenen geteilt werden, die als Scope (Gültigkeitsbereich) bezeichnet werden:

    • Anwendungs-Scope: Die Daten werden von allen Benutzern während der gesamten Lebensdauer des Servers geteilt (zum Beispiel die Liste der Ärzte);
    • Anfrage-Scope: Die Daten existieren nur für die Dauer einer Anfrage (das Modell einer View);
    • Client-Scope: Die Daten sind benutzerspezifisch und müssen von einer Anfrage zur nächsten erhalten bleiben (die gewählte Sprache, der angemeldete Benutzer).

    Der ursprüngliche Kurs ([ASP.NET MVC], 2013) verwendete für diesen letzten Scope eine Sitzung: einen vom Server verwalteten Speicherbereich, der jedem Browser zugeordnet ist. [ASP.NET Core] verwendet diesen Ansatz weiterhin ([AddSession]), aber dieses Dokument verzichtet, ebenso wie die Fallstudie, darauf: Daten mit Client-Scope werden vom Browser in Cookies gespeichert. Der Server behält zwischen den Anfragen desselben Benutzers keinerlei Daten: Man sagt, er sei zustandslos ([stateless]). Dadurch ist es zum Beispiel möglich, mehrere identische Server hinter einem Load Balancer zu betreiben. Der Preis dafür: Ein Cookie steht unter der Kontrolle des Benutzers, der es lesen und ändern kann. Deshalb werden dort nur unkritische Daten gespeichert – oder Daten, die vom Server signiert oder verschlüsselt werden, sodass dieser jede Änderung erkennen kann: Das ist beim [TempData]-Cookie (Beispiel 20) und beim Authentifizierungs-Token (Kapitel 8) der Fall.

    Auf der Serverseite entsprechen der Anwendungs- und der Anfrage-Scope den Lebensdauern der Services der Dependency Injection (siehe Beispiel 06). [ASP.NET Core] kennt drei davon:

    Registrierung
    Lebensdauer
    Eine Instanz ...
    AddSingleton
    Anwendung
    für die gesamte Lebensdauer der Anwendung, von allen Anfragen gemeinsam genutzt
    AddScoped
    Anfrage
    pro HTTP-Anfrage, von allen gemeinsam genutzt, die sie während dieser Anfrage anfordern
    AddTransient
    keine
    Bei jeder Injection: zwei Anfragen, zwei Instanzen

    namespace Example23.Services;

// Geltungsbereich ANWENDUNG (AddSingleton): eine einzige Instanz, von
// ALLEN Anfragen ALLER Benutzer gemeinsam genutzt
public class CounterService
{
    private int total;

    // mehrere Anfragen können GLEICHZEITIG laufen: Interlocked
    // garantiert, dass zwei gleichzeitige Inkremente nicht verloren gehen
    public int Increment() => Interlocked.Increment(ref total);
}
    • Zeile 7: Der Service wird ein Singleton sein (siehe [Program.cs]): Sein Feld [total] hat daher Anwendungs-Scope;
    • Zeile 11: Ein Webserver verarbeitet mehrere Anfragen gleichzeitig auf mehreren Threads ([threads]). Führen zwei Anfragen gleichzeitig [total++] aus, können beide denselben Wert lesen, und eine Erhöhung geht verloren. [Interlocked.Increment] führt Lesen, Addieren und Schreiben in einer einzigen, unteilbaren Operation aus. Ein Singleton-Service muss sich stets vor solchen gleichzeitigen Zugriffen in Acht nehmen.

    namespace Example23.Services;

// Geltungsbereich ANFRAGE (AddScoped): eine NEUE Instanz für jede HTTP-Anfrage,
// gemeinsam genutzt von allen, die sie WÄHREND dieser Anfrage anfordern
public class RequestService
{
    private static int createdInstances; // static: ein Zähler, der von allen Instanzen gemeinsam genutzt wird

    public int Number { get; } = Interlocked.Increment(ref createdInstances);
}
    • Zeile 7: Ein Feld mit dem Modifizierer [static] gehört zur Klasse und nicht zu einer Instanz; es wird von allen Instanzen gemeinsam genutzt. Es zählt die Anzahl der erzeugten Instanzen;
    • Zeile 9: Jeder Instanz wird bei ihrer Erzeugung eine Nummer zugewiesen. Der Service hat Anfrage-Scope: Die Nummer ändert sich mit jeder Anfrage.

    using Example23.Services;
using Microsoft.AspNetCore.Mvc;

namespace Example23.Controllers;

public record ScopesModel(int Total, int Instance, int Tool, int MyVisits);

public class ScopesController(CounterService counter, RequestService request, ToolService tool) : Controller
{
    [HttpGet("/")]
    public IActionResult Scopes()
    {
        // Geltungsbereich CLIENT: ein vom BROWSER aufbewahrtes Datum (Cookie),
        // das bei jeder Anfrage an den Server zurückgesendet wird
        int.TryParse(Request.Cookies["myVisits"], out var myVisits);
        myVisits++;
        Response.Cookies.Append("myVisits", myVisits.ToString(),
            new CookieOptions { HttpOnly = true, SameSite = SameSiteMode.Lax });
        return View(new ScopesModel(counter.Increment(), request.Number, tool.Number, myVisits));
    }
}
    • Zeile 8: Die drei Services werden injiziert;
    • Zeilen 15–18: der Client-Scope: ein in einem Cookie gespeicherter Zähler. [Request.Cookies["myVisits"]] liest das vom Browser gesendete Cookie ([null] beim ersten Besuch). [int.TryParse] wandelt es in eine Ganzzahl um; schlägt die Umwandlung fehl, wird [myVisits] auf 0 gesetzt. Die Action erhöht den Wert und setzt das Cookie neu;
    • Zeile 19: Die Werte werden an die View übergeben.

    Für einen Besuchszähler ist das belanglos. Bei sensiblen Daten (die Identität des Benutzers, seine Rolle) muss der Server Manipulationen erkennen können: Kapitel 8 zeigt, wie.

    Aus diesen Lebensdauern folgt eine Regel: Ein Service darf nicht von einem Service mit kürzerer Lebensdauer abhängen. Ein Singleton, das einen Service wie [Scoped] erhielte, würde ihn unbegrenzt behalten, weit über die Anfrage hinaus, für die er erzeugt wurde. [ASP.NET Core] prüft die Einhaltung dieser Regel beim Start im Entwicklungsmodus und verweigert den Start, wenn die Regel verletzt wird. In der Fallstudie:
